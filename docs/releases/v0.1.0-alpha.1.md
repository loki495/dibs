**This is an alpha.** It runs, it is tested, and the maintainer uses it daily, but schemas, MCP tool arguments and defaults can still change between alpha releases. Back up `database/database.sqlite` before every upgrade.

## What Dibs is

A self-hosted task tracker built for AI agents as first-class users. Any agent session, including a fresh one with no context, connects to the same host-local MCP server, asks what is open, claims a task, records plans, research and decisions as it works, and the next session picks up where the last one stopped. Local SQLite is the source of truth; GitHub Issues and Projects are an optional, asynchronous mirror.

## Main features

- **MCP tools and the claim lifecycle.** Create, list, peek, show, update and comment on tasks; plans and knowledge notes; claim, heartbeat, release and complete, so several agents do not duplicate work. A claim binds to the agent's real OS process and the UI shows whether it is still alive.
- **Local-only mode.** With no GitHub repository configured everything works against one local repository record, and nothing contacts GitHub. Work is organized with labels and parent tasks.
- **GitHub mirroring (optional).** Writes land in SQLite first and are pushed through a durable queue with retry and backoff that honours GitHub's rate-limit headers. Creates never duplicate: an ambiguously failed create is looked up on GitHub before it is retried. A first import adopts a local-only instance and queues everything created locally.
- **Activity log.** A browsable, filterable record of what humans and agents changed, with pruning.
- **PWA.** The workspace installs to a phone or desktop home screen and has a mobile layout.
- **Sample agent skill.** `skills/dibs/SKILL.md` teaches an agent cold start, plans, claims, and recording research and lessons.

## GitHub token scopes

Only needed for mirroring. See [Token scopes](../../README.md#connecting-to-github-optional) in the README (classic `repo` + `project`, or a fine-grained token with Issues and Projects read/write on the one repository).

## Container layout

`docker/setup.sh` starts three containers:

- `web` serves the UI over HTTP (no host PID namespace).
- `app` is where agents and Artisan commands run (`docker compose exec ... app ...`). It shares the host PID namespace and its main process, `dibs:claims:watch`, records claim liveness for the UI. It serves no HTTP.
- `scheduler` drains the GitHub push queue and prunes the activity log.

## Upgrade notes for existing installs

Back up first (see [Backup, restore and upgrade](../../README.md#backup-restore-and-upgrade)).

- **Move your Traefik labels, networks, ports and other HTTP overrides from `app` to `web`.** HTTP is now served by `web`; `app` exposes no port.
- **Run migrations.** `bash docker/setup.sh` does it, or `docker compose exec -T -u www-data app php artisan migrate --force`. Then `docker compose restart app web scheduler`.
- **Reconnect agent sessions** after the `app` restart; their MCP connections end with the container.
- **Changed defaults.** `GITHUB_PROJECT_NUMBERS` now defaults to none, so set it explicitly if you mirror Projects (a blank value used to be read as project 0). `DIBS_TIMEZONE` now defaults to `UTC`; set it if you relied on another zone. `.env.example` now ships neutral values: `APP_URL=http://localhost:8095`, blank `SESSION_SECURE_COOKIE` and `TRUSTED_PROXIES`. Review your own `.env` against it, especially behind HTTPS.
- **Cloudflare-routed requests are never auto-logged-in.** `AUTO_LOGIN_*` applies only to private-network requests with no Cloudflare edge header; anything arriving through Cloudflare uses the normal login.

## Known limitations

See [Known limitations](../../README.md#known-limitations): one repository per instance, a single shared workspace for all users, Linux `/proc` needed for verified claim liveness, no natural-language capture yet, no built-in backup tooling, and Areas, Groups and Priority only from GitHub Projects.
