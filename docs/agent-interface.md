# MCP agent interface

This is the contract for the host-local stdio MCP server, its read/write/claim tool surface, and the Artisan CLI fallback. Local SQLite is authoritative for issues, comments, labels, native parents, Project membership, Group, Priority, plans, tasks, and knowledge records. GitHub is an asynchronous, mostly-read-only mirror reached through a durable push queue — there is no inbound webhook receiver and no scheduled freshness polling.

## Server foundation

Dibs uses `laravel/mcp` `^1.0` (locked at v1.0.0). It targets the stateless 2026-07-28 MCP revision this project's claim/capability-token design assumes, serves legacy `initialize` clients alongside it, and implements the protocol itself, with no dependency on the separate official `modelcontextprotocol/php-sdk`.

## Registering the server

An agent launches the server as a stdio child process through the `app` service (the one with the host PID namespace; `web` only serves HTTP):

```bash
sh -c 'exec docker compose -f <path-to-dibs>/docker-compose.yml exec -T -u www-data -e DIBS_CLIENT_PID=$PPID app php artisan mcp:start todo'
```

The `sh -c` wrapper hands the agent's own PID (`$PPID`) to the server as `DIBS_CLIENT_PID`, so claim liveness tracks the agent rather than the container's shim. A plain `docker compose exec ...` without it still works, but a claim then stays alive until its lease expires.

The server name is `todo` (`Mcp::local('todo', TodoServer::class)` in `routes/ai.php`). `-T` is required because stdio carries the JSON-RPC stream. Copy-paste setups for Claude Code, opencode, Codex and Antigravity are in the README's "Connect an agent" section. A session must reconnect after the `app` container restarts, since the server is a process inside it. [`skills/dibs/SKILL.md`](../skills/dibs/SKILL.md) is the agent-side usage guide.

- Server: `App\Mcp\Servers\TodoServer`, registered in `routes/ai.php` via `Mcp::local('todo', TodoServer::class)`. Start it with `php artisan mcp:start todo`.
- `todo_status` (`App\Mcp\Tools\DescribeTodoServer`, backed by the `App\Actions\DescribeTodoServer` Action) is the health/metadata tool: app name/environment, the repository `mode` (`github` once a repository has been imported or when `DIBS_GITHUB_OWNER`/`DIBS_GITHUB_REPO` are set, `local` when the instance runs local-only), configured GitHub owner/repository, whether a GitHub repository has been imported locally (`imported`, `full_name`; always `false`/`null` local-only), and issue/label/project counts. Never returns `GITHUB_TOKEN` or any other secret.
- Verified end to end against the real stdio process (`php artisan mcp:start todo` piped raw JSON-RPC): a `tools/call` for `todo_status` returns real data in one clean JSON-RPC line with empty stderr; `tools/list` correctly lists it; an unknown method, a request missing the required `_meta` protocol-version member, and malformed JSON each return a structured JSON-RPC error (`-32601`, `-32602`, `-32700`) without crashing the process or corrupting the stream.
- **Known gap:** `laravel/mcp` has no `notifications/cancelled` handling: a cancellation notification is silently dropped as unrecognized. That is harmless while every tool handler is a short synchronous DB read; it matters only if a long-running tool is ever added.
- **Backward compatibility:** real MCP clients (Claude Code and opencode among them) still use the `initialize`-based handshake that predates the stateless `_meta`-based revision, which the spec expects servers to keep supporting. `laravel/mcp` handles the core of this natively: `JsonRpcRequest::isLegacy()` skips `_meta` validation for requests lacking it, and a default `Initialize` method answers the old handshake. `TodoServer` adds one thing: `App\Mcp\Methods\InitializeLegacyClient` extends `Initialize` to remember the connecting client's name via `App\Mcp\ClientIdentity`. Covered by `tests/Feature/Mcp/TodoServerLegacyInitializeTest.php`.

## Boundary

Agents run on the host and connect to a stdio MCP server. The server exposes Dibs tools and delegates to the same application Actions as the workspace. Those Actions write SQLite directly as the confirmed result and enqueue a GitHub push rather than calling the GitHub API inline. `php artisan todo:agent:*` is retained as a local recovery and smoke-test fallback. There is no unauthenticated HTTP API and no GitHub credential in an agent prompt, browser bundle, or command argument. The MCP server and CLI read the server-side `GITHUB_TOKEN` only when the push-queue worker needs it to reach GitHub.

Ten commands exist: `list`, `show`, `claim`, `claims`, `heartbeat`, `release`, `create`, `update`, `comment` and `complete`. Several MCP tools have no CLI equivalent (`todo_status`, `todo_context`, `todo_metadata`, `todo_search`, `todo_peek`, `todo_queue_status`, `todo_next`, `todo_scaffold_plan`, `todo_reopen`, `todo_claim_status`, `todo_report_bug`). The commands are:

- `todo:agent:list` — read current tasks, parent context, Group, Project, labels, Priority, and local push-queue state from SQLite.
- `todo:agent:show ISSUE` — read one task in the same shape as `todo_show` with `withComments` (first 50 comments), including untrusted-author withholding. `create` and `update` print the same shape for the written task.
- `todo:agent:claims --path=ABS... [--except-session=ID]` — list live claims whose claimed `paths` overlap the given absolute paths, as JSON (`[{issueId, agentName, paths}]`, `[]` for none); `--except-session` skips claims whose agent name ends in `:ID`. `--held-by=ID` instead lists every live claim (with or without paths) held by that conversation id. Read-only; the Claude Code overlap hook (`claim-overlap.sh`) calls it before an Edit/Write and the stop hook (`stop-gate.sh`) with `--held-by` before a session ends.
- `todo:agent:claim ISSUE --agent=NAME --pid=PID [--minutes=30] [--path=ABS]...` — claim a task for the calling agent's own OS process. Returns a `capability_token` in the response **once, in plaintext** — the caller must hold onto it; it's required for every subsequent `heartbeat`/`release` on that claim and is never shown again (only its hash is stored). `--pid` must be the calling agent's own real process ID — the server independently verifies it via `/proc` rather than trusting it blindly (see "Claims and checkpoints" below).
- `todo:agent:heartbeat ISSUE --pid=PID --token=TOKEN [--minutes=30]` — renew a live claim's lease. Re-verifies the process is still alive on every call; a claim cannot renew itself back to life once its process is confirmed dead.
- `todo:agent:release ISSUE --pid=PID --token=TOKEN --left=TEXT` — release a claim. Requires the exact capability token and pid returned by `claim`; nothing else can release another worker's claim. `--left` (what is left and the exact next step) is required and posted as a comment.
- `todo:agent:create TITLE [--body=] [--area=] [--parent=] [--group=] [--priority=] [--label=]* [--new-group=] [--new-label=] [--idempotency-key=]` — create locally with Project, Group, parent, labels, and Priority; enqueues the GitHub push.
- `todo:agent:update ISSUE --expected-revision= [--title=] [--body=] [--parent=ID | --clear-parent] [--new-group=NAME | --clear-group] [--area=ID | --area-name=TITLE | --clear-area] [--priority=ID | --priority-name=NAME | --clear-priority] [--add-label=]... [--remove-label=]... [--note=] [--idempotency-key=]` — title/body/Area/Group/Priority/parent/label patches (`--area=ID` or `--area-name=TITLE` or `--clear-area`; `--priority=ID` or `--priority-name=NAME` or `--clear-priority`, ids and names kept apart because Priority names are numerals; no other metadata fields yet; repeat the label options for several names); requires the `revision` last read for the issue and returns a non-error `{"conflict": true, "current": ...}` payload instead of failing on a stale revision. Writes SQLite and enqueues the push.
- `todo:agent:comment [ISSUE] --body= [--comment-id= --expected-revision=] [--idempotency-key=]` — add a comment (`ISSUE` required) or edit an existing one (`--comment-id`/`--expected-revision` required instead); same non-error stale-revision conflict payload as `update`. Writes SQLite and enqueues the corresponding GitHub push.
- `todo:agent:complete ISSUE --pid=PID --token=TOKEN --summary=TEXT [--reason=COMPLETED|NOT_PLANNED] [--result=JSON] [--force --force-reason=TEXT]` — closes a claimed task, enqueues the GitHub push, posts `--summary` as the closing note, and releases the claim. `--result` is the completion evidence as a JSON object; the completion guards apply as for `todo_complete` (see "Completion guards" below). Claim-scoped like `release`/`heartbeat`: only the exact process holding the live claim can complete it.

Output is always machine-readable JSON. Commands reject malformed IDs, unavailable local records, and wrong Project-field options before any write.

## Untrusted authors

Every read — each MCP tool and every `todo:agent:*` command — withholds the returned text written on GitHub by anyone who isn't the mirrored repository's owner or listed in `DIBS_TRUSTED_GITHUB_AUTHORS` (`App\Support\TrustedAuthors`). Such an issue's `title` becomes `[withheld from agents: written on GitHub by @login, not a trusted author]`, its `body` is `null`, its search `excerpt` is empty, and its summary carries `withheld: true`; such a comment keeps its place, `id` and `author` but its `body` is the same note and it carries `withheld: true`; such a closing note is `null`. Text with no GitHub author (created through Dibs, including every record in local-only mode) is always shown. Imported text from a deleted account is stored with author `ghost` and withheld. Withholding applies to what is returned, not to matching: `todo_search` still matches a withheld issue's title and body, so which issues match a query is visible (see the [security model](security-model.md)). The web workspace is unaffected.

## MCP tools

Registered on `App\Mcp\Servers\TodoServer`, in this order:

| Tool | Purpose |
|---|---|
| `todo_status` | Server/repository identity and record counts — call first to confirm identity. Takes a placeholder `noop` boolean — pass `true` (see below). |
| `todo_context` | Areas (Projects), Groups, labels, live claims, and push-queue counts — orientation before acting. Takes a placeholder `noop` boolean — pass `true` (see below). |
| `todo_metadata` | Everything attachable to a task: areas with open-task counts, Groups and Priority options with ids and areas, labels with ids/descriptions/usage counts, and the rules for attaching or creating each. Searchable by `query`; narrow with `kinds` and `area`. |
| `todo_list` | Filtered/paginated task or knowledge listing (state/search/view plus the shared filters: labels, areas, groups, parent tree). |
| `todo_search` | Keyword search across task, plan, and knowledge titles/bodies, including closed records, plus the same shared filters (the keyword query is optional when a filter is given); ranked summaries with excerpts. |
| `todo_peek` | Cheap batch check for whether cached records changed: `{id, title, revision, state}` per id, no body. `revision` only bumps on `todo_revise` (title/body/Area/Group/Priority/parent/labels) — compare `state` too if closing/reopening matters, since neither covers comments, claims or edits made elsewhere (the web UI). An id with no matching issue is listed under `unresolved`; a deleted issue is still returned, with `available: false`. |
| `todo_show` | Full detail for one issue, optionally with paginated comments; `maxBodyLength` truncates the body server-side (`bodyTruncated` says whether it did) for a cheap preview before committing to a full read. A closed issue's payload includes `closing: {reason, note, references, result, closedAt}` (all but `closedAt` are `null` when that close had no reason/note/evidence); `closing` is `null` for an open issue. Reopening and closing again reports only the latest close. |
| `todo_queue_status` | Pending/failed/needs-attention push-queue counts and per-item detail. |
| `todo_next` | The next step of a plan (`planId`) and its work order, or why none is ready; read-only. See "Next step and work order" below. |
| `todo_create` | Create a task, plan, or knowledge record; enqueues the GitHub push. Idempotency-key supported. Labels: `labelNames` (array of names, matched case-insensitively, created if missing and always stored lowercase with single spaces — no `todo_context` id lookup needed), `labelIds`, and the legacy single `newLabelName` combine into one de-duplicated set. |
| `todo_scaffold_plan` | Create a parent plan issue plus its child tasks atomically, in one transaction. `groupId`/`priorityId` set the plan issue's own Group/Priority, independently of each child's own. Its result (like `todo_show` of any issue with children) carries `stepLint`, see below. |
| `todo_revise` | Revise an issue's title/body/note/Area/Priority/Group/parent/labels/links with optimistic-concurrency (`revision`) protection; a stale write returns a non-error `{conflict: true, current: ...}` rather than erroring. `groupId` moves the issue to a different Group within its existing area (the issue must already belong to one) — `newGroupName` instead moves it to the Group of that name in its area (matched case-insensitively, created when missing) and `clearGroup: true` removes it from its Group; use at most one of the three. `areaId` / `areaName` (title, case-insensitive) moves the issue to another Area (Project) and `clearArea: true` removes it from its Area; an issue with no Area gets one the same way. A move keeps the old Area's membership out of the picture (a pushed one is queued for deletion on GitHub, an unpushed one retired locally, a previously retired one in the target is revived) and the new membership starts with **no Group and no Priority**, since those options belong to the old Area; nothing is mapped by name. Pass `groupId`/`newGroupName`/`priorityId`/`priorityName` from the new Area in the same call to set them at once. `priorityId` or `priorityName` (case-insensitive; Priority names are the numerals `1`–`5`) sets the Priority and `clearPriority: true` removes it, each queued to GitHub; the option must belong to the issue's (new) Area. At most one of each `area*`/`clearArea` and `priority*`/`clearPriority` group; an unknown or blank Area or Priority, an option from another Area, a Group/Priority on an issue with no Area, or `clearArea` combined with a Group/Priority change is a handled error that changes nothing. The change is logged in the change log (`Changed area`, `Changed priority`).` parentId` moves the issue under another local issue (cycle- and self-parent-checked, appended after its siblings) and `clearParent: true` detaches it; they cannot be combined. A blank Group name, an unavailable parent, or a Group change on an issue with no area is a handled error that changes nothing. `addLabels` / `removeLabels` (arrays of names, at most 20 each) are deltas, so labels the caller never saw are left alone: names match case-insensitively, are stored lowercase with single spaces, and a missing label in `addLabels` is created; a name in `removeLabels` the issue does not carry is ignored. A blank name, or one name in both lists, is a handled error. Knowledge labels (`research`, `lesson`, `decision`, `guide`) work the same, and adding one moves the issue to Knowledge. The change is queued to GitHub as one label difference (nothing is queued when it changes nothing, though the revision still bumps). |
| `todo_comment` | Add a comment, or edit one (`commentId` + `expectedRevision`) with the same stale-conflict shape as `todo_revise`, with a whole new `body` or with `replace` edits (see "Exact-string edits" below). |
| `todo_claim` | Claim a task for the calling process. Returns a `capabilityToken` once, in plaintext, and `workOrder`, the task's brief with the text of each linked rule this `agentName` has not yet received (see "Next step and work order"). `contextReset: true` makes it resend every rule. `paths` (up to 20 absolute files or directories the work will touch) is stored on the claim; `overlaps` in the result lists other live claims (unexpired, unreleased, process not confirmed dead) whose paths are the same as, an ancestor of, or a descendant of one of them, as `{issueId, agentName, paths}`. A warning only: the claim still succeeds. A relative path, `..`, NUL or more than 20 paths is a handled error. |
| `todo_heartbeat` | Renew the calling process's own live claim lease. Creates no GitHub comment or push-queue entry. |
| `todo_release` | Release the calling process's own live claim without completing the task. `left` (what is left and the exact next step) is required; it becomes the release's one comment, and a blank one is refused with the claim kept. |
| `todo_complete` | Close a claimed task, enqueue the push, and release the claim. `summary` becomes the closing note (a comment on the issue); optional `reason` (`COMPLETED`/`NOT_PLANNED`, pushed to GitHub as the close reason) and `references` (commit/PR pointers) add detail, ignored without `summary`. `result` carries the structured evidence, checked by the completion guards (see below); `force` + `forceReason` overrides them. |
| `todo_reopen` | Reopen a closed task: state back to `OPEN`, `state_reason` cleared (as GitHub does on a real reopen), a `reopen_issue` push enqueued. Not claim-scoped — takes just `issueId`, like the workspace UI's Reopen icon. Earlier closing notes stay in the comment history; `closing` in `todo_show` is `null` again. Returns the fresh `todo_show` detail. |
| `todo_claim_status` | Read-only: whether a task has a live claim, and by whom — no capability token exposed. Includes a direct liveness check (`isCurrentlyAlive`) and the background watcher's last recording (`recordedLiveness`). |
| `todo_report_bug` | Self-report a problem with the MCP/CLI tooling itself (not a product task) — creates an `agent report`-labeled issue; amend with `todo_comment`. |

Every write tool implements `Laravel\Mcp\Server\Contracts\Errable` and validates its own arguments via `Request::validate()` — `laravel/mcp` 1.0 does not enforce a tool's declared JSON Schema before calling `handle()`, so schema-shaped input alone is not a safety guarantee.

## Completion guards

`todo_complete` (and `todo:agent:complete`) refuse a completion that lacks the evidence the task's guard profile asks for (`App\Actions\CheckCompletionGuards`). The refusal is a handled error listing every missing field and what to pass; the issue stays open, the claim stays held and nothing is written. Closing from the web UI is never guarded: a person closing a task is the override.

`result` is `{commit, tests, docs, done_when_held}`: `commit` a 7-40 character SHA (format only; Dibs cannot see other repositories), `tests` `{command, exit_code}` with `exit_code` 0, `docs` a non-empty list of doc paths, `done_when_held` a boolean. `commit`, `tests` and `docs` may instead be the string `"none: <why>"`. Other keys are dropped. It is stored on the closing comment and returned as `closing.result`; a routine completion adds no comment besides the closing note.

| Profile | Requires |
|---|---|
| `floor` | a `summary` |
| `standard` (default) | a `summary`; with `reason: NOT_PLANNED` nothing more. A `commit` for tasks labeled `agent task` or `bug` and for plan steps (children of a `plan`-labeled issue). `tests` and `docs` whenever `commit` is a SHA, on any task. For a plan step, a `Done-when:` line in its body and `done_when_held: true` |
| `strict` | as `standard`, and `"none: ..."` is refused for `tests` and `docs` |

The most specific setting wins: a `Guards: <profile>` line in the task's body, then in its parent's body, then the task's Group in `DIBS_GUARDS_GROUPS` (comma-separated `Name=profile`, Group names case-insensitive), then `DIBS_GUARDS_DEFAULT`. A `Guards:` line in a body written on GitHub by an untrusted author is ignored, so imported text cannot lower the guard. An unknown profile name is itself a refusal.

A `"none: <why>"` reason and a `forceReason` must be a real reason: at least five words, and not only filler such as "force", "just close", "n/a", "not needed" or "testing" (`App\Support\RealReason`). `force: true` with such a reason closes despite the missing evidence, records a `CompleteTodoTask` entry "Guard overridden: <reason>" in the activity log (with the skipped checks), and appends the same line to the closing note.

## Exact-string edits

`todo_comment` (editing, with `commentId` + `expectedRevision`) and `todo_revise` accept `replace: [{from, to, all?}]` instead of a whole new body: the edits apply in order to the current text under the same `expectedRevision`, so a small change such as re-stamping an atlas comment's Verified at SHA never rereads or resends the whole text. Each `from` must occur exactly once, or every occurrence is replaced with `all: true`; a `from` that is missing or occurs more than once, or an edit that would make the text longer than 65535 characters, is a handled error naming the edit, and nothing is applied. A stale revision returns the usual `{conflict: true, current}`. `body` and `replace` cannot be combined. The response leaves the text out (`todo_comment` returns `id`, `issueId`, `revision`; `todo_revise` returns `id` and `revision`). The edit is pushed and logged like any other.

Note on `noop`: `todo_status` and `todo_context` have nothing to configure, but Claude Code's `canUseTool` callback failed calls whose input was an empty object ("invalid permission result"). Passing any argument avoided it, so both tools declare one boolean, `noop`, that the handler never reads (`App\Mcp\Tools\Concerns\DeclaresPlaceholderArgument`). It is `required` in the schema so a model always sends it — an optional one would just be omitted — but `laravel/mcp` does not enforce the schema, so callers that leave it out still succeed.

Note on `pid`: the MCP protocol itself has no session/process identity a server can read from a tool call, so `todo_claim`/`todo_heartbeat`/`todo_release`/`todo_complete` never accept a pid argument. `App\Mcp\CallerPid` resolves it: the client passes its own PID in the `DIBS_CLIENT_PID` environment variable of the MCP command (see "Registering the server"), used while that process exists; otherwise the server's parent process (`posix_getppid()`), which is the connecting client only for a bare `php artisan mcp:start`. Under `docker compose exec` the parent is the container's containerd shim, which outlives the agent, so without `DIBS_CLIENT_PID` a dead agent's claim never reads as dead and only lease expiry frees it. The CLI fallback has no equivalent (each Artisan invocation is its own short-lived process, not the long-running agent), so it requires an explicit `--pid=` naming the calling agent's own process — the shared Actions underneath verify whichever PID they're given the same way regardless of which surface it came from.

Every tool takes and returns the **local id** (the SQLite primary key, shown as "id N" in the web UI); the GitHub issue number is a different, mirror-assigned value that is null until pushed and never lines up with the local id. The web UI search box accepts either, while `todo_search` matches title/body text only. Every tool returns structured JSON with stable local IDs, GitHub URLs when pushed, and push-queue status when relevant. On a local-only instance every tool works the same against the local repository; nothing is queued, so records never get a GitHub URL or number. Stdio is local-only; no network listener, browser credential, or MCP tool argument contains a GitHub token.

## Picking up work cold

This is the primary way a new session (or a different agent/tool entirely) is meant to start, not a fallback path: call `todo_context` first for orientation (areas, Groups, labels, live claims, push-queue snapshot), then `todo_list` — with no filters for everything open, or `area`/`group`/`parentId` to scope to one project — to see what's actually outstanding. No prior conversation state, plan file, or hand-off note is required; the tools are the hand-off. Filter `todo_list` by `label: "agent task"` to see only work suited to an agent picking it up unattended (code changes, audits, drafting, research, investigation) and skip tasks that need a human body or a judgment call only a human can make (errands, purchases, in-person chores). A task's absence of `agent task` isn't a hard block — read it and use judgment — but it's a useful default filter, and an agent creating a task via `todo_create`/`todo_scaffold_plan` should apply the label when the new task fits.

## Finding related material

Call `todo_search` with `{"query":"queue retries"}` to search tasks, plans, and knowledge together. Every whitespace-separated term must occur in the title or body (terms may match different fields). Matching uses literal substrings with SQLite's ASCII case-insensitivity: `%` and `_` are literal characters, and quotes/operators have no special meaning. Comments are not searched.

`todo_search` and `todo_list` share one set of filters, which combine with each other and with the text query:

- **Labels:** `labels` (the result must carry every one), `anyLabels` (at least one), `excludeLabels` (none). Names match case-insensitively, since labels are stored lowercase. The older single `label` still works and counts as one more `labels` entry.
- **Projects and Groups:** `areas` and `groups` take id lists, `areaNames` and `groupNames` take names (case-insensitive, and a Group name matches in every Project that has a Group of that name); a result may be in any of the listed ones. The older single `area` and `group` still work.
- **Trees:** `parentId` narrows to that issue's direct children; with `descendants: true` it means the whole tree beneath it (the parent itself is not included).
- Each list holds at most 20 entries of at most 100 characters; a malformed value is a validation error naming the argument (for example `anyLabels.0`).

Use `todo_metadata` first to discover what an `areaNames`/`groupNames`/`labels` value could be, or to get an id for `areas`/`groups`/`labelIds`: it lists every area with its Groups and Priority options, and every label with its id, description and usage counts, plus the rule for attaching or creating each. `query` matches names (and label descriptions); `kinds` (`areas`, `groups`, `priorities`, `labels`) and `area` narrow the response. An unknown `area` id is a validation error, not an empty result.

`state` defaults to `ALL` (including closed knowledge and completed work); use `OPEN` or `CLOSED` when needed. When area and group are both supplied, they must match the same available Project membership. A label that does not exist is not an error: the page comes back empty and the response carries `unresolved` (for example `{"labels": ["agnt task"]}`), so an empty result can be told from a typo. `unresolved` is absent when every name matched.

Results use the `todo_list` pagination shape (`items`, `page`, `perPage`, `total`, `lastPage`), defaulting to 15 results and capped at 50. More query terms matched in the title rank first, with local ID ascending as a stable tie-breaker. Each item includes the usual issue summary (including labels, knowledge flag, and parent ID) plus an `excerpt`: up to 240 body characters around the first body match, with ellipses when truncated. Title-only matches show the beginning of the body, or an empty excerpt if there is no body. Use `todo_show` only for selected results that need full detail.

A query is at most 200 characters. It may be omitted, or blank, when at least one filter is given, and results then list in id order with the start of each body as the excerpt; with no query and no filter the call is rejected as an error on `query`. This first version scans local titles/bodies without a search index or external service; it provides keyword matching, not semantic similarity. `todo_list` keeps its existing task/knowledge views and title/issue-number search behavior. Search is currently exposed through MCP, with the shared `SearchTodoIssues` Action available to other application entry points.

## Claims and checkpoints

The local-only `agent_sessions` and `task_claims` models bind a task to an explicit worker identity with an expiry and renewal time. A claim is not a GitHub lock: it prevents accidental duplicate local-agent work sharing one local database. This contract is explicitly scoped to multiple agents/processes on **one** local database — it does not arbitrate ownership across independent databases or between different users. Multi-user/multi-instance collaboration is intentionally kept open as a future direction, but no distributed conflict-resolution design exists yet. A worker must post concise checkpoint comments for a material result, decision, blocker, or verification result, never raw tool logs.

**Step template and lint:** a plan's child steps are written with the sections `Objective`, `Files likely` (paths, classes, methods), `Tier`, `Done-when` (a checkable rule: what must be true and what evidence is recorded), `Evidence` (what the closing note records), `Rules` (linked records, not pasted text) and `Blocked-by`; a section is a line starting `Name:` (bold, heading or list markers allowed). `todo_show` of an issue with children, and so the `todo_scaffold_plan` result, includes `stepLint`: for each open leaf child lacking `Done-when`, `Files likely` or `Evidence` (or leaving it empty), `{id, title, missing}` naming the sections. It only flags; nothing is rejected. The checked sections are `App\Support\StepTemplate::REQUIRED`.

**Step fields:** `Done-when`, `Evidence` and `Files likely` can also be kept as data: `step: {doneWhen?, evidence?, filesLikely?}` on `todo_create`, `todo_revise` and each `todo_scaffold_plan` child (only the keys given change; `null` or blank clears one; the body is never touched; at most 4000 characters each). An empty field falls back to its body line, for `stepLint`, the Done-when completion guard, `todo_show` and the work order alike. `blockedBy` lists the sibling steps (same parent) a step waits on: local ids on `todo_create` (with `parentId`) and `todo_revise`, where it replaces the whole list (`[]` clears it); on `todo_scaffold_plan` children, the 0-based positions of earlier children in the same call. A self, cross-plan, missing or cyclic blocker is a handled error that changes nothing. A field or blocker change bumps `revision` like any `todo_revise` and is logged in the change log. `todo_show` returns `step: {doneWhen, evidence, filesLikely, blockedBy: [{id, title, state}]}` when any of them is set (by field or body line). The web detail panel shows the fields and blockers read-only.

**Next step and work order:** `todo_next(planId)` walks the plan's children in plan order, skipping containers (children with children of their own) and steps by untrusted authors, and returns the first that is open, not held by a live claim (an expired lease or a verified process that is gone counts as free, the same test `todo_claim` applies) and has every blocker closed: `{ready: <work order>, reason: null, waiting: [...]}`. When none is, `ready` is `null` and `reason` is `plan_done` (no open step), `all_claimed`, `blocked`, or `mixed`; `waiting` lists each open step passed over as `{id, title, claimedBy?, blockedBy?: [open blocker ids]}`. An id that does not exist, or has no steps, is a handled error. The work order (`DescribeWorkOrder`) is `{step: {id, title, revision, state}, plan: {id, title}, objective, tier, repos, doneWhen, evidence, filesLikely, blockedBy: [{id, title, state}], rules: [{id, title, revision?, text?}], otherLinks: [{id, commentId, title, labels}], lastCheckpoint: {id, createdAt, text}|null, truncated, rulesPending?, hint?}`: `tier` and `repos` are read from a `Tier:` and a `Repo:`/`Repos:` anywhere on a body line (up to the next ". Name:" or the end of the line); `repos` falls back to the plan's body. `objective` is the `Objective:` line, else the start of the body (800 characters); `rules` are the step's links to issues labeled `rule`; `lastCheckpoint` is the newest comment that is not a closing note (600 characters). It stays under 6000 characters (about 1500 tokens) apart from rule text, which has its own 12000-character budget: the longest texts are shortened and other links dropped, and `truncated` says so. `todo_next` gives rules as id and title only. `todo_claim` (and `todo:agent:claim`, as `work_order`) gives each rule's `text` (the rule statement only, without its Trigger/Check/Applies to/Source/Merged candidates lines) only if this `agentName` has not yet received that rule at its current revision, and records the delivery; a revised rule is sent again, and a rule left out of the rule-text budget is listed in `rulesPending` (with a `hint` to `todo_show` it) and not recorded, so its text comes on the next claim. Deliveries are kept per agent name, not per claim, so a session that claims several steps gets each rule once per context; after a context reset (compaction, `/clear`, resume) pass `contextReset: true` (`--context-reset` on the CLI) to clear them first.

**Links between records:** an issue can link explicitly to other issues, or to one comment of another issue, so a session is handed exactly the rules, lessons, research, decisions, guides and related tasks that apply to it rather than text pasted into bodies or every sibling. Links live in `issue_links` (`from_issue_id`, `to_issue_id`, optional `to_comment_id`) with no relation-kind column: a target's kind is read from its labels. They are local only, never pushed to GitHub, and written by `SyncIssueLinks` (shared by `todo_revise`'s `addLinks`/`removeLinks`, `todo_create`'s and each `todo_scaffold_plan` child's `addLinks`, and the workspace detail panel). Duplicates are ignored, removing a missing link is ignored, and a self link, a missing or unavailable target, a comment that is missing, unavailable or belongs to another issue, or adding and removing the same link in one call is a handled validation error that changes nothing. `todo_show` returns `links` and `linkedBy` (each item `id`, `number`, `title`, `withheld`, `state`, `labels`, `knowledge`, `commentId`, `summary`), at most 50 per direction, `summary` being one line capped at 160 characters from the linked comment or the issue body; text from an untrusted GitHub author is withheld like any other agent-facing text. Unavailable targets are hidden and a deleted record's links cascade away. The workspace detail panel lists links with remove buttons, a title/number/id search to add one, and a "Linked from" list; it replaced the former implicit "related knowledge" list of knowledge-labeled siblings.

**Workspace claim/plan visibility:** the issue detail panel shows a live claim's agent name, host, pid, its liveness, and whether its lease has expired — all from `DescribeTodoClaim`, the same Action `todo_claim_status` uses. Liveness comes from a fresh `isCurrentlyAlive` re-check (via `LinuxProcessLiveness`, distinct from the `isVerifiedLive` flag recorded at claim time) where host PIDs are visible; in the `web` container, which can't see them, it falls back to what the watcher recorded (see **Recorded claim liveness** below): "alive · checked 20 seconds ago", "process gone · checked …", or "(liveness unverifiable)" when there's no recording or it's stale. A "Release claim" button calls a `ReleaseAbandonedTaskClaim` Action: a human-authorized override with no capability-token check, distinct from the agent-facing `ReleaseTaskClaim` — the workspace is behind login for one operator, who already has full local database access, so this just gives a safe, auditable UI path to recover a claim judged abandoned. The panel also shows parent/child navigation (a knowledge-labeled child is flagged directly in the children list), the explicit links described above, and a pending-sync badge linking to a push-queue visibility page rather than duplicating its detail.

**Hardened claim identity:** a claim binds to the caller's real OS process, not a self-reported string. `App\Services\Process\LinuxProcessLiveness` reads `/proc/<pid>/stat` directly to confirm a claimed pid genuinely exists and matches the start time recorded when the claim was made — a PID that's since been reused by an unrelated process cannot keep an old claim (or its heartbeat) valid. This requires the process doing the check to see host PIDs, since agents run on the host while Dibs runs in a container — without that, `/proc` inside the container only reflects the container's own PID namespace and can't verify anything about a host-side process. In `docker-compose.yml` only the `app` service (`dibs-app`, the exec target for `mcp:start` and `todo:agent:*`) has `pid: "host"`; it runs no web server. The `web` service serving the workspace has no host PID access and sets `DIBS_PROCESS_LIVENESS=false`, so `LinuxProcessLiveness::currentlyAlive()` returns null there and the UI shows what the `app` watcher last recorded for the claim (see **Recorded claim liveness** below) rather than checking it; "liveness unverifiable" appears only when there is no recording or it is stale. Claim, heartbeat, takeover and `todo_claim_status` all run in `app`, where the check works. When liveness genuinely can't be verified (that setting removed, or a container/namespace situation where it doesn't apply), a claim still succeeds but is flagged `is_verified_live: false` — treated as weaker assurance, never auto-reclaimed as "dead," only as expired.

**Recorded claim liveness:** the `app` container's main process is `php artisan dibs:claims:watch` (`WatchClaimLivenessCommand`), which every `DIBS_CLAIM_LIVENESS_INTERVAL` seconds (default 30, or `--interval=`) checks each live, unexpired, verified claim's process and stores the result on the claim (`task_claims.liveness_alive`, `liveness_checked_at`) through the `RecordClaimLiveness` Action. Expired, released and never-verified claims are skipped. It stops within about a second of SIGTERM, logs a SQLite "database is locked" pass as a warning and retries on the next one, and treats any other error by `APP_DEBUG`: with debug on it rethrows, so the error surfaces with its normal output (and the command exits); with debug off it reports it through the normal exception handler and carries on, so the container agents exec into stays up. With `--once`, a pass that failed either way exits non-zero. `ResolveClaimLiveness` combines the two sources for `todo_claim_status`, the detail panel and the task-list pill: `isCurrentlyAlive` is the direct check (null where it can't run), `recordedLiveness` is `{alive, checkedAt, isStale}` or null before the first check, with `isStale` true once the recording is older than `DIBS_CLAIM_LIVENESS_STALE_AFTER` seconds (default 90, three intervals), and `displayAlive` is the direct check, else a fresh recording, else null. The recording is display-only: claim takeover (`ClaimTaskForAgent`) and heartbeat (`HeartbeatTaskClaim`) act only on a definite `false` from their own direct check, never on a recorded value, which can be up to a stale interval old and could predate a PID reuse. A person who sees "process gone" in the UI can use "Release claim".

Claims and session metadata are local durable data that GitHub never holds, so they are backed up with the SQLite database.

## Retry and conflict rules

- Reads are always against local SQLite and are retry-safe.
- A write commits to SQLite immediately as the confirmed result and enqueues a push-queue row; the command does not wait on GitHub.
- A write given an idempotency key commits atomically with its receipt: a retry with the same key returns the original record, a failed call leaves no record and no receipt, a concurrent duplicate returns the first call's record, and a key reused for a different kind of write (e.g. a comment key on a create) is a validation error.
- A push-queue row that GitHub rejects (validation error, missing access) is marked `needs_attention` for human review rather than retried into a duplicate or silently discarded. A transient failure (rate limit, network, 5xx) is retried with backoff, waiting for GitHub's own `Retry-After`/`X-RateLimit-Reset` on a rate limit, and only marked `needs_attention` once its retry budget is spent. A create that timed out or hit a 5xx is looked for on GitHub before it is sent again, and adopted if found, so a retry never duplicates an issue, comment, label or Group; when that can't be told, the row goes to `needs_attention` instead. Neither rolls back the local write. See `architecture.md` for the budget.
- Pushes are last-local-write-wins: a remote edit made since the last pull is overwritten.
- Updates patch only requested fields, locally and in the resulting push. A push rejection does not roll back the local write; it surfaces via the queue.
- A command records the agent identity and intent in the local record before a multi-step write.
- Nothing on a schedule creates, edits, completes or comments through the MCP surface; an agent explicitly invoking a tool or command is always the trigger. The push-queue drain to GitHub is a separate background process, not an agent write.

## Website convention

A website is a Group inside a Project area. Its meaningful parent issue holds repository/path/context links. Work is child issues; granular work is nested children. Lessons, research, and decisions are labeled issues in that Group, with evidence and records in comments. Planned, not built: a `website_bindings` table that maps a website to explicit repository paths, so names alone never select a checkout.
